# ЮKassa: настройка и проверка

## Перед запуском

Интеграция для самозанятого НПД: готовая страница ЮKassa, одностадийная оплата (`capture: true`), без сохранения карт и автосписаний. Чеки «Мой налог» администратор оформляет самостоятельно. Поле `receipt` для онлайн-кассы в запрос не передаётся.

Сделайте резервную копию БД. Загрузите бэкенд и новую сборку фронтенда одновременно в режиме обслуживания, выполните:

```sh
/opt/php/8.4/bin/php artisan migrate --force
/opt/php/8.4/bin/php artisan optimize:clear
```

Новые пакеты Composer не нужны. Миграция сохраняет прежние оплаты, добавляет заказы и журнал доставки уведомлений. Автоматический откат запрещён, поскольку он удалил бы финансовую историю.

## Тестовый магазин

Только в серверном `.env` (не в Git, не в настройках сборки фронтенда):

```dotenv
YOOKASSA_ENABLED=true
YOOKASSA_MODE=test
YOOKASSA_FRONTEND_URL=https://oscalendar.ru
YOOKASSA_TEST_SHOP_ID=идентификатор_тестового_магазина
YOOKASSA_TEST_SECRET_KEY=секретный_ключ_тестового_магазина
YOOKASSA_TEST_USER_IDS=числовой_ID_тестового_пользователя
```

`TEST_USER_IDS` — ID пользователей OSCalendar, не Telegram, не табельные номера. Несколько ID разделяются запятой. По умолчанию список пуст и никто не может создавать тестовые платежи. Используйте отдельный тестовый аккаунт: успешный тест действительно выдаёт ему доступ, но не списывает денег. Администратору покупать подписку нельзя — у него уже полный доступ. Обычных клиентов в этот список не добавлять.

В тестовом магазине: **Интеграция → HTTP-уведомления**:

- URL: `https://oscalendar.ru/api/payments/yookassa/test`
- События: `payment.succeeded`, `payment.canceled`, `payment.waiting_for_capture`.

После изменения `.env` снова выполните `artisan optimize:clear`. Убедитесь, что HTTPS webhook доступен извне без авторизации/проверки браузера и POST-запросы не блокирует защита хостинга. Секреты в URL не используются: обработчик сам получает платёж по API ЮKassa и проверяет магазин, тестовый режим, номер заказа, валюту, сумму и статус.

Для платежей cron не нужен: после подтверждения по API и фиксации оплаты приложение сразу отправляет уведомления администраторам. Платёжные команды не включены в расписание. Для ручной сверки и повторной отправки после сбоя:

```sh
/opt/php/8.4/bin/php artisan payments:reconcile
/opt/php/8.4/bin/php artisan payments:notify
```

Первый восстанавливает незавершённые операции, второй доставляет неотправленные сообщения. Для одного заказа: `payments:notify --order=UUID`. Без нового webhook или ручного запуска фонового повтора доставки нет. Активные администраторы определяются по роли `administrator`. Telegram учитывает настройку профиля и привязанные аккаунты, push — включённые устройства. Настройки бота и VAPID остаются прежними. Тестовые сообщения явно говорят «ТЕСТОВЫЙ платёж — не доход».

## Что проверить в тестовом магазине

1. Купить базовую/расширенную подписку тестовой картой из документации ЮKassa. Проверить переход и возврат, срок, уровень и историю.
2. Не возвращаться на сайт после оплаты: webhook должен активировать доступ и отправить уведомление без cron.
3. Повторить webhook: одна оплата, одно предоставление доступа и один набор уведомлений.
4. Изменить цену после создания заказа: открытый заказ остаётся по старой цене; следующая покупка — по новой.
5. Отменить оплату: доступ не появляется; незавершённый заказ доступен в профиле для проверки.
6. Продлить подписку с остатком менее трёх месяцев: новый период начинается на следующий день после последнего оплаченного.
7. Повысить базовую подписку: доплата за все ещё не завершившиеся базовые периоды по ценам, сохранённым в заказе; даты не сдвигаются. Отдельная запись доплаты не даёт дополнительного срока.
8. Отключить доставку уведомления: подписка выдаётся независимо. Повторный webhook или ручной запуск может повторить неуспешную доставку (до 10 попыток, интервал не менее 5 минут). Успешные каналы не повторяются.

Гарантируется однократное применение платежа в БД. Как и у других внешних уведомлений, при обрыве связи после фактической доставки, но до получения подтверждения, редкий повтор сообщения полностью исключить нельзя. Для push применяется стабильный тег заказа.

## Боевой режим

После проверки заполнить `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY`, изменить `YOOKASSA_MODE=live`. В боевом магазине настроить те же события на `https://oscalendar.ru/api/payments/yookassa/live`. Не удалять тестовые ключи, пока остаются незавершённые тестовые заказы. Режим и магазин сохраняются в каждом заказе; нельзя просто подменить ID магазина для уже начатых заказов.

После изменения настроек очистить кэш конфигурации. `YOOKASSA_ENABLED=false` запрещает новые заказы, но не препятствует обработке уже созданных оплат.

## Исключительные ситуации и ограничения

- Если исходные периоды отменили/изменили во время доплаты или аккаунт заблокирован, деньги фиксируются, но доступ автоматически не меняется. Страница результата и комментарий в общей истории показывают необходимость проверки; администратор получает предупреждение. Разрешение такого конфликта — ручная сверка, не повторная оплата.
- Создание платежа повторяется с тем же ключом и неизменным телом. Если ответ о создании потерян, после 23 часов POST больше не повторяется (ЮKassa хранит идемпотентность 24 часа). Не удалять такой заказ и не создавать замену вслепую: найти платёж в ЮKassa по `metadata.order_id`, дождаться/повторить уведомление или согласованно восстановить `provider_id`, затем запустить сверку.
- Одновременно допускается один незавершённый заказ на пользователя, чтобы не смешивать повышение с покупкой/продлением. Его можно открыть из профиля. Отмена или завершение подтверждаются провайдером, не кнопкой в браузере.
- Уведомления не являются чеками. В боевом сообщении есть пользователь, табельный номер, сумма, дата в часовом поясе администратора, вид операции, тариф/срок и ID платежа для сверки с «Мой налог».
- Онлайн-платёж нельзя отменить кнопкой отмены ручной записи. Возвраты выполняются отдельно в кабинете ЮKassa; автоматическая обработка возвратов и отзыв доступа по ним **не входят в эту реализацию**. Возврат нужно сверять и корректировать доступ отдельно, не считая его автоматически отменённым в OSCalendar.
- Приложение не получает номер карты/CVC. Секретный ключ хранится только на сервере. Во время разработки реальные или тестовые ключи пользователя не использовались; проверка с настоящим тестовым магазином обязательна до боевого запуска.
