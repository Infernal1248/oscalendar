# Уведомления Telegram и Web Push

В профиле два независимых канала: Telegram включён по умолчанию для существующих и новых пользователей; push выключен, пока пользователь сам не подключит текущий браузер. Можно выбрать оба канала, только один или выключить оба. Настройка Telegram относится к автоматическим сообщениям об изменениях рабочего плана и подтверждении ознакомления, а не к ответам бота на команды или одобрению регистрации.

## Развёртывание

1. Загрузить бэкенд и установить зависимости из `composer.lock`:

   ```bash
   composer install --no-dev --optimize-autoloader
   /opt/php/8.4/bin/php artisan migrate --force
   ```

2. Один раз создать пару VAPID-ключей:

   ```bash
   /opt/php/8.4/bin/php artisan push:keys
   ```

   Скопировать выведенные `WEBPUSH_PUBLIC_KEY` и `WEBPUSH_PRIVATE_KEY` в `.env`. Добавить:

   ```dotenv
   WEBPUSH_SUBJECT=https://oscalendar.ru
   ```

   Приватный ключ не публиковать и не добавлять в git. Сохранять оба ключа при последующих развёртываниях: замена потребует переподключения устройств. Команда `push:keys` только выводит новые значения, `.env` автоматически не меняет.

3. Применить конфигурацию:

   ```bash
   /opt/php/8.4/bin/php artisan config:cache
   ```

4. Собрать фронтенд для `/` с `VITE_API_URL=/api` и загрузить **всё содержимое `dist`** в `public` бэкенда. В том числе `push-sw.js`, `manifest.webmanifest`, `images` и `index.html`. Эти файлы должны открываться по HTTPS без авторизации и SPA-подмены. JS service worker не должен обслуживаться как HTML.

5. Существующий cron `artisan schedule:run` должен выполняться каждую минуту. В расписание добавлена `push:send`; второй cron при уже работающем планировщике не нужен. Проверить:

   ```bash
   /opt/php/8.4/bin/php artisan schedule:list
   ```

6. В своём профиле включить push и нажать «Отправить тестовое уведомление». Без VAPID-ключей кнопка подключения недоступна, но Telegram продолжает работать.

Хостинг должен иметь исходящий HTTPS-доступ к службам браузеров: Google FCM, Apple Web Push, Mozilla Push и Microsoft WNS. Telegram VDS-мост не используется и не изменён. Отдельный постоянно работающий queue worker не нужен.

## Поведение

- Android/десктоп: открыть профиль в поддерживаемом обычном браузере, включить push и разрешить уведомления. Браузер внутри Telegram может не поддерживать push.
- iPhone/iPad: iOS/iPadOS 16.4+, добавить сайт из Safari на домашний экран, открыть с иконки и включить push в профиле. Manifest добавляет запуск как веб-приложения, но не офлайн-доступ.
- В профиле push настраиваются отдельно для каждого устройства. При явном выходе из аккаунта подписка текущего браузера отключается; на других устройствах сохраняется.
- Push не зависит от платной подписки, но требует активного пользователя и права `history.view`, как уведомления об изменениях в Telegram.
- Планировщик проверяет существующие события хронологии, не создаёт новые события и не запускает парсер. Telegram и push не блокируют друг друга.
- Передаются краткое сообщение без ФИО/содержимого расписания и ссылка на `/history`. По нажатию открывается кабинет; просмотр и ознакомление проверяются обычными правами приложения. Тестовое сообщение ведёт на `/profile`.
- Отправляются новые ожидающие ознакомления события и подтверждения после подключения устройства, не старый архив. Устаревшие версии и прошедшие месяцы пропускаются. Кандидаты ограничены последними 24 часами, срок доставки сообщения у провайдера — 1 час.
- Успешные отправки учитываются отдельно для каждого устройства и события. Временные ошибки повторяются раз в 5 минут, максимум 5 попыток. Сбой не помечается успешной отправкой. Ответы 404/410 отключают истёкшую подписку; пользователь может включить её заново.
- Как и любой внешний push, доставка не гарантирует ни мгновенного показа, ни ознакомления. При аварии между принятием сообщения провайдером и записью результата возможен повтор; одинаковый `tag` объединяет сообщения одного месяца на устройстве.
- Это не механизм обновления ICS: частоту загрузки календарной ссылки определяет календарное приложение.

## Проверки

Бэкенд: `php artisan test --filter=WebPushTest`. Все данные тестов находятся в SQLite `:memory:`; реальные сообщения не отправляются. Проверяются настройки, доступ, шифрование, повторные попытки и обработка истёкших устройств.

Фронтенд: `node --test tests/*.test.mjs`; `tests/notifications.browser.mjs` с установленным Playwright проверяет переключатели и адаптивную сетку на фиктивных данных. Реальную доставку на iOS/Android необходимо проверить после настройки production-ключей.
